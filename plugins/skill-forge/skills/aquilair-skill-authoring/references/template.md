# SKILL.md 填空模板（第 4 步专用）

> 参照样板：解释型看 `plugins/business-hub/skills/fnb-inventory-analysis/SKILL.md`，受控执行型看 `plugins/business-hub/skills/mfg-transfer-allocation/SKILL.md`。

## 目录结构约定

```text
<skill-name>/
├── SKILL.md          # 必需：核心指令（工具、探查循环、铁律、流程），50~120 行
├── references/       # 按需加载，分层承载：接口行为手册 / 业务语义卡 / 场景剧本 / 交付细化
├── scripts/          # fetch_meta.py 等可执行助手（有元数据服务时必配）
└── assets/           # 模板、夹具等静态资源（目前各技能尚未用到，预留）
```

## frontmatter 模板

```yaml
---
name: <kebab-case-技能名，必须与目录名一致>
description: <一句话中文定位>。Use when the user asks about <中文触发关键词枚举>——any question about <English keywords>. 数据来自 MCP 服务 <服务名>（<只读 / 含写操作，须走确认卡>）。仅限业务问答：<开发类请求不属于本技能>——not for development tasks like <典型开发请求>, even if the topic involves <业务主题>.
license: Proprietary — Aquilair 内部分发，仅限公司内网使用
---
```

### description 写作规范（唯一触发入口，三原则）

1. **主动一点**：模型天然欠触发，触发关键词宁可多列（同义说法、口语说法都放进去），不要指望模型「猜到」该用技能。
2. **中英混合句式**：中文触发词用「Use when the user asks about …」枚举，英文关键词用「any question about …」兜底——参照 fnb / mfg 现行写法。
3. **负向边界**：误触发一律用「not for …」句式治（写在 description 尾部 + 正文定位段重复一句），不用保守措辞治。

## 章节骨架（两型对照，按需取用）

| 章 | 解释型（fnb） | 受控执行型（mfg） |
| --- | --- | --- |
| 标题 + 定位 | 一句话定位 + 否定句 + 开发边界句 | 同左 + 加总边界句 |
| 数据环境 | —（无） | **必配**：生产 vs 沙箱定义、参数位置坑（如 `sandbox` 顶层）、混用禁令 |
| 工具表 | 服务名 + 全限定工具名 + 参数 + 用途，读写标注 | 同左；写操作工具标「**写操作，必走确认卡**」 |
| 探查循环（**两型标配**） | 以 MCP 实时查询为唯一事实源（不信快照/文档记录值/记忆值）：①元数据先行（轻量清单起步、属性级按需 neighborhood）→ ②结合问题规划查询 → ③取实例 → ④观察是否足以回答、不足迭代（换属性实名/扩过滤/下钻/补元数据），**终止判据=足以回答即停**；报错按码自纠；`fetch_meta.py` 为非必需缓存刷新器，缓存与实时冲突以实时为准 | 同左 |
| 专有语法 | filter 语法表（场景/规则/示例三列） | 同左（可压缩为一行示例） |
| 铁律（Gotchas） | 禁止重判、只读边界、名称展示、不存在实体三步 | 证据优先、写前确认、默认沙箱、写后回查、错误可能发生在写入之后、不扩大动作 |
| 回答前决策 | 复用/重查判据 | 并入「确认与执行流程」 |
| 确认与执行流程 | —（无） | **必配**：准备→备沙箱→出卡→等确认→串行执行回查，五步按序 |
| 确认卡模板 | —（无） | **必配**：见下节五要素 |
| 输出规范 | 中文先结论后证据、来源标注、单据号逐字核对、表格行数上限、Emoji 表 | 同左 |
| 按需加载 | 何时读哪个 references 文件，逐条列触发条件 | 同左 |

### 确认卡模板（受控执行型必配，五要素）

```markdown
## ⚙️ 操作确认

| 项目 | 内容 |
| --- | --- |
| 执行环境 | 沙箱 `{sandbox_id 或名称}`（默认） |
| 动作链 | `{action_name_1}` -> `{action_name_2}` |
| 关键参数 | `{parameter_name}={value}` |
| 影响 | {对业务对象的预期变化} |
| 不可逆性 | {沙箱可丢弃；生产为不可逆真实写入} |

💡 回复「确认」将在**沙箱环境**执行；如需写入**生产环境**，请回复「确认，在生产环境执行」。
```

用户已明确指定生产环境时，环境行与结尾提示改为生产警示（不可逆真实业务写入）。

## references 分层标准（第 2 步产物的形态约束，2026-10-30 定标）

- **接口行为手册**（facts.md）：DSL 语法最终版、工具行为、服务状态与能力边界、元数据缺陷、脏数据**模式**（模式级 + 挂工单 + 修复即删）。**禁止**数据实态快照（数值/条数/状态/回写与否）与时间戳日志章节——实测原始记录落目标仓 `evals/runs/`。
- **业务语义卡**（domain-model.md）：只载元数据查不到的业务文档编译（业务链/判定链语义/决策枚举/编码字典/规则公式口径）；实体/属性/关系/规则清单不维护副本（实时 `metadata_list_*` 为唯一权威）。
- 稳态 = 剧本（playbook）+ 交付细化（delivery）+ 接口行为手册 + 业务语义卡，四件小而稳，全部不随数据量与时间线性增长。

## 写作风格四条（写每一段前对照）

1. **祈使句**：直接说「读 X 再做 Y」，不写「你应该考虑读 X」。
2. **铁律配 why**：每条铁律带上根因或后果（「必须 X，否则 Y」）。发现自己在一遍遍加粗、全大写强调时，通常是规则没讲清而不是不够响——回头补解释，不加音量。
3. **例子胜过规则**：凡要求特定输出格式（表格列、确认卡、名称展示「中文名称（编码）」），放一个字面示例，让模型照抄结构而不是猜。
4. **行数预算**：SKILL.md 全文 50~120 行；超预算先问「这段是每次都需要，还是特定场景才需要」——后者拆 references，在「按需加载」节写清触发条件。
