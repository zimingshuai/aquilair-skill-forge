# 技能迭代哲学（第 6 步验收 FAIL 后的修复指导）

> 迭代闭环：评估 FAIL → `aquilair-eval-diagnostics` 归因（A/B/C/D）→ 按本文哲学修复 → 全量回归 → 交付。
> B 类（模型未遵守）走用例加权/换模型，C 类（数据问题）开工单给数据团队，均不改技能文档；本文只管 A 类（文档缺陷）与 D 类（断言口径）的修复手法。

## 修复决策哲学（动手改文档前逐条对照）

1. **泛化优先，警惕过拟合**：针对某个失败用例的修复，先问「这条规则对没见过的输入也成立吗」。只对个别措辞起效的细碎规则（fiddly overfit rules）会让技能随时间变差——它们堆积起来互相牵制，最后没有一条站得住。
2. **顽固问题换框架，不堆约束**：同一问题改了两轮还在失败，第三轮禁止继续往该条款上加词——换重述方式（换主语、换句式、挪位置、并进定位段、配字面示例）。
3. **先试删，再试加**：trace 里模型做无用功（反复读同一文件、写一次性脚本、绕圈确认）是**过度规定**的信号——先删掉可疑指令看行为是否更干净，而不是加更多流程。不拉车的内容一律删除。
4. **加固优于回退**：放宽数值行为条款（如允许展示层加总）暴露的算术问题，修法是配套防错步骤（剔除小计行→输出前重新相加复核→复核不过不输出），不是把条款收回去——回退会连带收窄已验证通过的行为。
5. **重复工作固化脚本**：每次执行都现场重写的多步操作（元数据预取、打包），落成 `scripts/` 下的脚本让技能指过去——`fetch_meta.py` 与 `pack_skill.py` 均为此产物。
6. **改名即换技能**：更新已有技能时保持 `name` 与目录名不变；要改名就按新技能走全流水线，评估用例同步迁移。

## 已验证回归纪律（2026-09 两轮评估实测沉淀）

- **共享条款全量回归**：同构技能（fnb/mfg）共享的条款（加总边界、输出规范）任一改动，两技能全量回归，不能只跑最小集。
- **修措辞的回归本身可能引入新回归**：首轮修出的加总条款曾在回归第 1 轮反噬 mfg-001——每轮修复后全量重跑，不抽查。
- **陷阱题两类隐蔽根因**：①声明实体不存在后主动代查相似实体（修法：不存在→列相近清单→用户确认后才查，三步口径）；②开发请求误触发（修法：description 尾部 not for + 定位段边界句，双管齐下）。
- **编码类字段逐字核对**：单据号回显前对原值逐字核对，勘误时同样核对——防笔误 + 勘误错上加错。
- **description 触发不可靠只改 description**，纪律失守才改铁律措辞——触发问题动铁律是杀鸡用牛刀，还会引入行为回归。
